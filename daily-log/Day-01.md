# 1일차 — 프로젝트 설명 및 Uber 공격 체인 분석

**Project: uber-identity-zero-trust-hardening**
> MFA Fatigue 및 세션 토큰 탈취 공격을 차단하는 Zero-Trust Identity & Session Hardening 인프라 구축

**환경**: VirtualBox VM(`growth`) · Ubuntu 24.04 LTS · 2 vCPU / 6GB RAM · Python 3.10+ / Envoy Proxy / Nginx
**참고 사고**: 2022년 9월 Uber 침해 사고 (Lapsus$ 계열 위협 행위자)

---

## 왜 이 프로젝트를 시작했나

학교 보안 시간에 실제 침해 사고 사례를 조사해서 발표하는 과제가 있었다. 큰 주제를 제로트러스트(Zero-Trust)로
잡고 사례를 찾던 중 발견한 게 2022년 Uber 침해 사고였다. 발표 자료를 준비하면서 이 회사가 어떤 과정과
이유로 뚫렸는지 하나씩 파고들다 보니, 단순히 "이런 사고가 있었다"에서 끝내기 아까웠다. 직접 이 공격을
막는 방어 시스템을 만들어보고 싶다는 생각이 들었고, 그게 이 프로젝트의 시작이다.

이전 프로젝트에서 Trivy로 컨테이너 이미지의 CVE를 잡아내고, Cosign으로 이미지 서명·검증까지 해봤다.
공급망(Supply Chain) 보안은 어느 정도 감을 잡았으니, 이번엔 방향을 바꿔서 **신원(Identity)과 세션(Session)** 계층을
직접 파고들어보기로 했다.

이 사고가 흥미로웠던 이유는, 공격자가 제로데이나 정교한 익스플로잇을 쓴 게 아니라는 점이다.
**MFA 알림을 새벽에 계속 눌러대는 방식**만으로 내부망 깊숙이 들어갔다. 기술적 결함이 아니라
"인증에 성공하면 그 뒤로는 다 믿어버리는" 설계 자체의 문제였던 것이다. 그래서 이번 프로젝트는
이 공격 체인을 5단계로 쪼개서 분석하고, 각 단계를 실제로 막는 컴포넌트를 하루씩 만들어보기로 했다.

## 공격 체인 5단계

```
[1] 자격증명 탈취  →  [2] MFA Fatigue  →  [3] 계정 접근 성공  →  [4] 세션 토큰 탈취  →  [5] 내부 확산
```

**Stage 1. 자격증명 탈취**
협력업체 직원의 계정 자격증명이 유출된 것으로 추정된다. 단일 비밀번호에만 의존하는 구조라
유출 자체를 막기는 어렵다. (이 프로젝트 범위 밖이라 참고만 하고 넘어간다.)

**Stage 2. MFA Fatigue (MFA 폭탄 공격)**
탈취한 계정으로 짧은 간격에 로그인을 반복 시도해서 피해자 휴대폰에 Push 인증 요청을 연속으로 쏟아붓는다.
새벽에 알림이 계속 오니 피해자는 지쳐서 눌러버리고, 공격자는 "IT 지원팀"을 사칭해 Slack으로
"안 눌러주면 계속 온다"는 식으로 압박까지 했다고 한다. 근본 원인은 대부분의 Push 기반 MFA가
**Number Matching(화면에 뜬 숫자를 확인하고 입력) 없이 단순 승인/거부 버튼만 제공**한다는 것.
→ 2일차에 `mfa_policy.py`에서 이 부분을 직접 막아본다.

**Stage 3. 계정 접근 성공**
MFA를 통과하는 순간 VPN 내부망 접속이 열린다. 문제는 인증에 성공한 이후 **어떤 디바이스로,
어디서 접속했는지에 대한 검증이 전혀 없다**는 것. "인증 성공 = 전면 신뢰"라는 오래된 Perimeter 방식의 한계다.
→ 4일차에 Envoy Proxy L7 계층에서 Device Posture 검증을 붙인다.

**Stage 4. 세션 토큰 탈취**
공격자는 내부 공유 드라이브를 뒤져서 PowerShell 스크립트에 하드코딩된 관리자 자격증명을 찾아냈고,
이걸로 PAM, Duo, AWS, GCP, vSphere까지 순서대로 접근했다. 세션 토큰이 **어느 IP/디바이스에서 발급됐는지와
전혀 묶여있지 않아서** 탈취된 토큰을 아무 데서나 재사용할 수 있었던 것.
→ 3일차에 `app.py`에서 DPoP 방식으로 토큰을 발급 시점의 IP/Client Key에 암호학적으로 묶어본다.

**Stage 5. 내부 확산**
결국 Slack 전사 공지 채널, HackerOne 버그바운티 리포트(미공개 취약점 포함), 내부 재무 시스템까지
사실상 다 열렸다. 한 번의 인증 성공이 조직 전체에 대한 암묵적 신뢰로 확장돼버린 것.
→ 6일차 통합 테스트에서 앞서 만든 방어 계층들이 실제로 이 확산을 몇 단계에서 끊어내는지 로그로 증명해본다.

## 공격 단계 ↔ 방어 컴포넌트 매핑

| 단계 | 근본 원인 | 대응 파일 | 예정일 |
|---|---|---|---|
| MFA Fatigue | Number Matching 부재 | `auth-server/mfa_policy.py` | 2일차 |
| 세션 토큰 탈취 | 토큰이 발급 환경에 안 묶임 | `auth-server/app.py` (DPoP) | 3일차 |
| 계정 접근 성공 | 인증 후 컨텍스트 재검증 없음 | `envoy-proxy/envoy.yaml` | 4일차 |
| 내부 확산 | 암묵적 전면 신뢰 | 통합 테스트 + 로그 | 6일차 |

## 이번 프로젝트에서 지킬 Zero-Trust 3원칙

1. **명시적 검증** — Push 승인만으로 신뢰하지 않고, Number Matching 등 능동적 확인을 거친다.
2. **침해 가정** — 토큰은 언제든 털릴 수 있다고 전제하고, 발급 환경과 암호학적으로 묶어서 다른 곳에서는 무용지물이 되게 한다.
3. **최소 권한 / 컨텍스트 기반 접근** — 로그인 성공이 곧 전체 접근 허용으로 이어지지 않도록, 매 요청마다 디바이스 상태를 다시 확인한다.
